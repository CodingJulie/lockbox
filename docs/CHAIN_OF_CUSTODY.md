# Целостность экспорта / Integrity export

Этот документ описывает, как Lockbox обрабатывает материалы от записи на устройстве до экспорта ZIP-архива с манифестом и хешами.

This document describes how Lockbox handles materials from capture to a ZIP export with a manifest and hashes.

## 1. Что хранится / What is stored

| Слой                  | Содержание                                                  | Кто видит plaintext       |
| --------------------- | ----------------------------------------------------------- | ------------------------- |
| Браузер               | Код доступа, DEK и сессия только в RAM                      | Пользователь              |
| Клиентское шифрование | AES-256-GCM содержимого и метаданных (имя, MIME)            | Только владелец кода      |
| Сервер / Supabase     | Ciphertext, nonce, обёрнутый DEK, тип, размер, `createdAt`  | Никто без кода            |
| Журнал `vault_events` | `login` / `upload` / `download` / `verify_fail`, HMAC от IP | Оператор видит хеш, не IP |
| Очередь offline       | Ciphertext в IndexedDB, TTL 1 час                           | Без кода не читается      |

Платформенные бэкапы Supabase копируют **уже зашифрованные** объекты. Это не замена client-side encryption: без мнемоники wrapped DEK бесполезен.

## 2. Временные метки / Timestamps

- `createdAt` материала и события журнала выставляет **сервер** (рантайм Vercel / Node, часы синхронизируются по NTP) в UTC ISO-8601.
- Экспорт архива запрашивает `GET /api/time` (`source: lockbox-runtime`) и записывает это время в `manifest.json`.
- Это **не** метка RFC 3161 (timestamp authority).

## 3. Архив / Export archive

Экспорт (кнопка в хранилище, право `download`) собирает на устройстве ZIP без сжатия (ZIP STORE):

```
manifest.json          формат lockbox-court-package-v1, время, список файлов
hashes.sha256          SHA-256 каждой выгрузки (plaintext, как его видит получатель)
files/001-…            материалы после расшифровки на клиенте
```

Целостность проверяется так: `sha256sum -c hashes.sha256` после распаковки. Хеш считается по содержимому файла в ZIP, не по ciphertext на сервере.

В манифесте **нет** кода доступа и полного vault id.

Формат `lockbox-court-package-v1` — внутренний идентификатор манифеста, не пользовательский текст.

## 4. Цепочка / Custody steps

1. Пользователь создаёт хранилище. Мнемоника остаётся у него; сервер получает только `vaultId` (SHA-256 derived key) и HMAC-proof.
2. Загрузка: клиент шифрует файл DEK, шлёт ciphertext. Сервер ставит `createdAt` и пишет `vault_events.upload` с HMAC(IP).
3. Хранение: объект в bucket `evidence`, строка в `evidence`. Имя файла в БД не хранится в открытом виде.
4. Гостевой доступ: отдельный sub-код с правом read/download; каждое скачивание — `vault_events.download`.
5. Экспорт: владелец (или гость с правом download) на доверенном устройстве собирает ZIP. Манифест фиксирует время экспорта с `/api/time`.
6. Передача: архив и хеши можно отправить любым удобным способом; целостность проверяется по `hashes.sha256`.
